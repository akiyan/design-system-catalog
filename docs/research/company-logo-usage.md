# 企業ロゴ掲載の事前調査

調査日：2026-11-20（日本時間）

対象サイト： https://design-system-catalog.akiyan.tokyo/

目的：トップページのグリッドと一覧行で、デザインシステムの提供元を識別するために企業ロゴを表示できるか検討する。スポンサー・公式提携の表示ではない。

調査対象：掲載中67システム。うち企業提供49件について公式ブランドページ・規約を探索。AdobeのSpectrum 2とReact Aria、ByteDanceのSemiとArco等は共通提供元。行政・国際機関15件、コミュニティ3件は別扱い。法的意見・権利者からの許諾取得ではなく、公開規定に基づく運用上の事前調査である。

## 結論と企業別サマリー

**全社の企業ロゴを一括取得・一括掲載するのは避け、条件を確認できた提供元から段階的に採用する。** 未確認・要申請の提供元は文字表示を維持する。

統合側でも確認した代表例：

| 提供元 / システム | 公式資料 | 今回の用途での判断 |
|---|---|---|
| Airtable / Blocks SDK UI | [Trademark Guidelines](https://www.airtable.com/company/trademark-guidelines) | **条件付き採用候補**。Airtable Marksの定義にロゴを含み、記事・Webサイトでの情報提供目的の参照を明示許容。無改変、正確な説明、帰属表示、非提携の誤認防止等が必要。規定が認めるロックアップを使用。 |
| Microsoft / Fluent 2 | [Trademark and Brand Guidelines](https://www.microsoft.com/en-us/legal/intellectualproperty/trademarks) | **事前確認・許諾側**。ロゴ等の多くの利用にライセンスが必要と明記。製品名のテキスト参照が許容されることと、企業ロゴを置けることは別。 |
| Cloudflare / Kumo | [Trademark Guidelines](https://www.cloudflare.com/trademark/) | **書面許諾が必要**。製品を特定する参照で許可されるのはword marks。Web Badges例外を除くロゴ利用にはwritten permission。Cloudflare Pagesで配信していることはKumo提供元ロゴの許諾とは別。 |

## 判断基準

### 1. 企業ロゴとデザインシステムのロゴは別物

- Microsoftの企業ロゴとFluent、AdobeとSpectrum、IBMとCarbonは別のアートワーク。片方の配布・許諾をもう片方へ流用しない。
- OSSのMIT / Apache等は、企業ロゴ・商標の使用許諾まで意味しない。製品のリポジトリ内に画像があるだけでも不十分。
- GitHubのアイコンやSNS共有アイコンについての限定許可を、「GitHubがPrimerの提供元であると示す企業ロゴ」に転用しない。
- headlessライブラリやコミュニティ製品に、架空の企業ロゴや自作のブランド代替ロゴを割り当てない。

### 2. プレスキットの存在と用途の許可を別々に確認

公開キットがある場合でも、報道限定・編集用途限定・事前承認・登録ユーザー限定等があり得る。一般公開の比較カタログが自動的に「報道」「editorial」に該当するとは判断しない。

運用上は次の4状態で管理する。

| 状態 | 意味 | 掲載前の対応 |
|---|---|---|
| 条件付き採用候補 | 公開規定に関連する紹介・参照用途の許容を確認 | 対象画像・用途・サイズ・余白等の全条件を照合してから有効化 |
| 事前確認・申請 | 明示的な承認制、または報道等の用途該当性が未解決 | 想定画面とURLを添えて照会し、回答を保存 |
| 規定未確認 | 配布元は見つかったが規約未確認、JS・認証・403・404等 | 文字の提供元名を維持。別ブラウザや問い合わせで確認 |
| 用途不適合 | 現時点の規定では今回の使い方を許容しない | ロゴ非掲載。別途許諾を得られた場合のみ再判定 |

「条件付き採用候補」は掲載承認済みを意味しない。全社を同じ条件で一括採用する方針は採らない。

ここでいう「確認が必要」は安全側の運用判断であり、すべての参照表示に法律上必ず個別許諾が必要だと断定するものではない。商標の指示的使用や著作権の例外が成立するかは、法域・具体的な表示・広告性等に依存する。本調査では、それらの例外だけを根拠に全社のロゴを掲載可能と判定していない。

## トップ・一覧に置くときの設計上の注意

1. **カード内の提供元表示に限定**する。サイト全体のヒーローに企業ロゴを並べてスポンサーのように見せる使い方は、同じ素材でも別用途として確認する。
2. **一律16〜24pxの正方形に押し込まない**。ワードマークには最低幅・余白規定がある。許容寸法を確保できない行では文字だけにする。切り抜きや縦横比変更はしない。
3. **ブランド色を勝手に変更しない**。モノクロ化・CSSフィルタ・背景色との合成・独自バッジ化を避け、公式に配布された適切なバリエーションを使う。
4. **ロゴのリンク先を記録**する。企業サイトへのリンクが条件の場合、クリック全体がカタログ詳細へ移動するカードだけでは条件を満たさない可能性がある。提供元リンクを独立させるか、文字だけにする。
5. **非提携の明記は補助**。「各ロゴ・商標は各権利者に帰属。本サイトは独立したカタログであり、掲載企業による後援・承認・提携を示すものではありません。」等は誤認防止には役立つが、許可の代わりにならない。
6. **素材は権利確認後に公式から取得**する。検索画像・ロゴ集約API・Simple Icons等のライセンスだけを根拠に企業ロゴを採用しない。favicon抽出も許諾の回避にはならない。
7. **公開リポジトリへの同梱も確認**する。ブラウザでの表示、ローカル保存、GitHubでの再配布、改変は別の行為になり得る。サイトのコードライセンスがロゴに及ばないことを明示し、再配布できない素材はコミットしない。
8. 隣に同じ提供元名がある装飾ロゴは通常 `alt=""` にして読み上げ重複を避ける。ロゴだけのリンクには提供元名のアクセシブルネームを付ける。

### 特に小サイズ表示へ影響する実例

[デジタル庁のロゴ規定](https://www.digital.go.jp/applications/logotype)では、基本形は高さ50 CSS px以上、省略形は20 CSS px以上。省略形には使える条件もあり、事前申請が必要。全ロゴを同一の小さい丸アイコンに揃える設計が成立しない具体例である。

## 実装へ進む際の管理案（今回は未実装）

企業・提供元単位のブランド台帳を用意し、システムIDから参照させる。公開データにあるOSSライセンス項目とロゴ許諾項目を混ぜない。

記録する情報：

- 対象企業・ロゴの正式名称、関連するシステムID
- 素材配布元URL、規約URL、実際に使用する素材のURL・版
- 利用目的（トップのカード、詳細左一覧、日英、リンク先）
- 許諾状態・確認日・次回確認日
- 申請先と回答の証跡（個人情報・メール全文は公開リポジトリに置かない）
- 最小幅/高さ、余白、背景色、使用可能なカラー/単色版
- クレジット・商標表記・リンク要件
- ホスティング・公開リポジトリへの再配布可否

表示は許諾確認済みのものだけを有効化するホワイトリスト方式。未確認・未承認・寸法不適合の企業は、現在の文字表記を残す。
